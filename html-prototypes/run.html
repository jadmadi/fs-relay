Run it

Two binaries, two commands, one mount. No root, no kernel modules beyond FUSE 3.

How do I get it running? Build both binaries, serve a directory, mount it — then run the smoke checklist at the bottom of this page. Everything between is flags and details.

Build

go build -o fs-relay ./cmd/fs-relay
go build -o fs-relay-bind ./cmd/fs-relay-bind

Or the production build with just build. Put fs-relay on the storage machine and fs-relay-bind on every client. There is no cross dependency, so putting both everywhere is fine. ~/.local/bin or /usr/local/bin are good homes.

Linux only. Nothing in this tree runs on macOS yet: the mount needs the Linux-only splice path, and the server uses Linux-only syscalls throughout. The analysis of what each bridge would take lives in ROADMAP.md.

Serve a directory

mkdir -p data/demo /mnt/fs-relay
./fs-relay -listen 127.0.0.1:8080 -data data -token local-demo
FlagDefaultMeaning
-listen127.0.0.1:8080 address to listen on
-datadata directory holding one folder per namespace
-token— shared secret; omit it and the server prints one
-token-file— read the secret from a file only you can read
-version— print the build version and exit
-h— print the usage and exit

Each name under data is one independent tree. The server creates -data if it is missing, but it never creates data/<namespace> — create each one before a mount joins it, or the mount is refused.

A secret you pass yourself is at least 8 characters: letters, digits, hyphens, underscores. Capitals count as different characters. Leave -token off and the server prints a secret on its error stream; copy that value onto every mount. A restarted server prints a new one.

Keep the secret out of the process list

install -d -m 700 ~/.config/fs-relay
(umask 077; openssl rand -hex 16 > ~/.config/fs-relay/token)
./fs-relay -token-file ~/.config/fs-relay/token

Why a file. A -token value sits in ps aux, readable by every local user. A mode-600 file is not. The process stops if the file is missing, not regular, larger than 4 KiB, empty, or readable by group or other.

Mount it

./fs-relay-bind -url http://127.0.0.1:8080 -ns demo \
  -token local-demo /mnt/fs-relay
FlagDefaultMeaning
-urlhttp://127.0.0.1:8080 server address; a bare host:port gets the http scheme
-nsdefault which tree under data/ to mount
-token / -token-file— the server's secret; one of them is required
-postoff send each operation as its own request instead of the single connection
-wsoff same as the default; passing both with -post is an error
-raw=falseon keep large reads and writes on the main connection
-allow-otheroff let other users on this host use the mount
-force-existing-mntoff mount over a non-empty directory
-debugoff log FUSE traffic

The mount checks its mountpoint before connecting: a missing path, a non-directory, or a non-empty directory stops it. A missing or wrong secret stops it too — it never retries a refused token. The server records the machine and the reason. Flags go before the mountpoint; a flag after it stops the mount with a hint.

Open the server URL in a browser for a welcome page. curl against the same URL returns a short status. Unmount with:

fusermount3 -u /mnt/fs-relay

What you get on the mount

  • A normal directory: create, read, write, rename, symlink, delete.
  • One connection per mount — the faster way to run it.
  • Several hosts mount the same name at once and see the same files.
  • SQLite works with its default rollback journal. PRAGMA journal_mode=WAL fails: WAL needs a shared-memory file this filesystem cannot provide.
  • Writes reach other mounts when the file is closed or synced.

Smoke checklist

On a new mount, in order:

0 / 6 verified
  1. Create a directory; write and read a small file.
  2. Make a symlink, rename it, delete it.
  3. Mount the same name a second time. Write on one, read on the other.
  4. Copy a file from one path on the mount to another. Append with >>.
  5. Write about 10 MiB with dd bs=10k and read it back.
  6. Repeat that write with -raw=false and compare the bytes.

Locks, with two mounts of one name:

0 / 3 verified
  1. flock -n on the second mount fails while the first holds the file.
  2. An fcntl write lock on one mount makes the other's write lock fail with EAGAIN until released.
  3. A SQLite database opened through both mounts, in rollback journal mode, commits from both sides, and PRAGMA integrity_check returns ok on each.

Advisory only. A lock binds mounts, not processes. A program opening the files under data/ directly is outside the lock table. See Locks.

Once both checklists pass, the mount is ready for real work. To understand what runs underneath, read Wire next.
