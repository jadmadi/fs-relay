Locks

Advisory byte-range locks with one authority: the server's table. That is what SQLite's rollback journal needs.

How do two mounts exclude each other? One server-side lock table per namespace, keyed by mount plus process — so SQLite's rollback journal works across mounts. Waits never hold a stream; drops heal by replay.

Who holds a lock

  • A holder is the mount's client id plus the kernel owner. Classic POSIX locks are per process, so two opens of one process share an owner — but two mounts never do.
  • The mount advertises POSIX locks, so the kernel keeps no lock table of its own: every lock call reaches the server.
  • The server is the only writer under data/. A process opening those files directly is outside the table.

The three bytes SQLite locks

  • A new reader read-locks the pending byte, then the shared range, then unlocks the pending byte.
  • Exclusive is a write lock on the shared range. It upgrades the same owner's own read lock there, without waiting for that owner's pending or reserved lock to clear.
  • A partial unlock of one of those three ranges splits the remaining bytes onto the overflow list, so the counts stay exact.
  • flock uses the same record as a whole-file entry. It conflicts with other flock locks and never with a byte-range lock.

Waiting without holding a stream

  • setlk and setlkw both try once and return EAGAIN on a conflict. The mount waits, then calls setlkw again; a release wakes every mount.
  • A release is one event, sent only when a mount is waiting on an inode in that namespace. A commit nobody waits on sends nothing.
  • The wake-up is a coalescing broadcast: a release closes the channel and installs a new one, so every waiter wakes and the reader never blocks.
  • getlk reports the first conflicting lock, or F_UNLCK when the range is clear. It never blocks.

How locks are dropped

What happensWhat drops
close a handle locks taken through that handle — FUSE carries no owner on release, so the handle stands in. A failed close still drops them.
release with an fh every lock that handle's owners hold on that inode
release with an owner, no fh that owner's locks — a read-only open takes no server handle, so it remembers only the owners that locked through it. A cat cannot drop a worker's locks on the same mount.
a mount does not rejoin all its locks, when the 8s hold expires

An owner tracks up to two handles with an overflow, so any recorded close drops it.

Proven with SQLite

Two mounts, four writers split across them, committed 200 rows with four distinct markers, and PRAGMA integrity_check was ok from both mounts. A reader on one mount held a transaction for 2s and a writer on the other waited 1.4s, then committed, with no database is locked. A new reader was held at the pending byte while a writer waited, then granted after it finished. Killing a mount that held a write lock released it after 8s. flock conflicted and released across mounts.

WAL stays out: it needs shared memory between processes, which the mount does not provide. The rollback journal is the supported mode.
