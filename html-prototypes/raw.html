Raw path

A read or write past a threshold moves its bytes on a separate TCP connection, so the kernel can splice them. Metadata stays on the main connection.

How do large transfers stay fast? Bytes inside a size window ride a separate TCP connection, where the kernel splices them without copying through the server process. Smaller bytes stay on the envelope; a failure retries there once.

The size window

Computed once, when the server starts, from the data directory — and sent to the mount on the handshake:

Min = clamp(32 × st_blksize, 64 KiB, Max)
Max = min(1 MiB, pipe size granted), minus 64 KiB
      when that still leaves at least 64 KiB
  • The mount uses the raw path when the byte count is inside [Min, Max].
  • Anything smaller — or a server that does not offer the path — stays on the FlatBuffers envelope.
  • -raw=false on the mount does not dial it.

Routing

Handshake

The mount opens a TCP connection and upgrades it:

GET /raw/<namespace> HTTP/1.1
Host: <host>
Connection: Upgrade
Upgrade: fs-relay-raw/1

The server checks the namespace, hijacks, refuses the connection if any body bytes were already buffered, and answers:

HTTP/1.1 101 Switching Protocols
Connection: Upgrade
Upgrade: fs-relay-raw/1
Fsr-Raw-Min: <min>
Fsr-Raw-Max: <max>

After that the socket is not HTTP. A missing Upgrade header is 400.

Headers

Request header, 40 bytes, little-endian. A write request is that header plus exactly length file bytes.

OffsetTypeField
04 bytesmagic FSRQ
4u16op: 1 read, 2 write
6u16reserved, 0
8u64inode, for a read without a handle
16u64fh — always for a write, for a read when set
24i64offset
32u32length, at most Max
36u32reserved, 0

Reply header, 16 bytes, little-endian. A successful read is followed by exactly length bytes. An errno reply has length 0 and no body.

OffsetTypeField
04 bytesmagic FSRP
4u32errno, 0 on success
8u32length: bytes that follow (read) or were written (write)
12u32reserved, 0

A bad magic, an unknown op, a nonzero reserved field, a length of 0, or a length above Max closes the connection. A filesystem error does not.

One transfer at a time

  • The server moves a read into a pipe before writing the reply, so a short read at end of file is the length in the header. Then it splices that pipe to the socket.
  • A write is spliced from the socket into a pipe and from the pipe into the file at offset. A host filesystem that refuses the splice into the file is copied from the pipe instead. A successful write publishes the same eviction as write.
  • The mount splices a read reply into a pipe and hands that pipe to FUSE — which splices it on into /dev/fuse — when the pipe can hold the reply. Otherwise it reads the reply into the FUSE buffer.
  • A write the mount sends is one writev of the header and the bytes FUSE already delivered.

Rules of the pool

  • The mount keeps up to eight raw connections. Each handles one transfer at a time.
  • A transport error is retried once on the envelope. A read or write at an offset is safe to repeat.
  • copyfilerange is the same family but not this connection: one copy_file_range(2) between two open files at the two offsets, a short count returned as success, the destination name evicted.
