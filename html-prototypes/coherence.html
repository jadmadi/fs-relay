Coherence

Every mount caches. The server tells every mount what changed. A mount that misses the news recovers on its own.

How do mounts stay consistent? Mounts cache aggressively; the server pushes an eviction on every change; a mount that misses one rejoins and replays.

Reads: list once, fetch ahead

  • readdir carries each name's attributes. The lookup and getattr that follow are answered locally — until an eviction drops them.
  • After a listing, the mount calls reads for the regular files in it of at most 64 KiB: ≤32 names and 1 MiB per call. A larger file stays a normal read.
  • Bodies are kept until an eviction for that name, and held at most 64 MiB.
  • Child directories are fetched with readdirs, ≤32 per call; a later readdir of one is answered from that. At most 8192 listings are kept.
  • A read-only open takes no server handle: read names the inode, and that open's flush and release stay on the mount. Opening a directory takes none either.

Writes: held, then sent once

A write is acknowledged by the mount and sent when:

  • contiguous bytes reach 1 MiB,
  • a write is not contiguous,
  • or on fsync, release, a read, a setattr, or a copyfilerange of that file.
  • flush reports an earlier send error and does not itself send.
  • release sends any bytes still held and closes the server handle in that one call.
  • Closing one descriptor while another of the same file stays open leaves those bytes on the mount until the last release — or one of the sends above.
  • Other mounts see the bytes once they are sent. A failed send is reported by the next write, and by close or fsync.

Server invalidates

The server publishes after a successful create, mkdir, symlink, write, setattr, unlink, or rmdir, after a release that carried file bytes — and after a rename it sends the old name and then the new name. A refused call sends nothing.

A name this mount itself just created, wrote, or changed is left in place: the saved body is dropped and page cache is invalidated, the listing is dropped, but the name stays. A missed eviction leaves cached bytes stale until the kernel drops the pages; names and attributes recover within the 1s timeout.

Drops heal

  • POST. The server writes a heartbeat on the join stream every 2s. A mount that receives nothing for 6s rejoins: the first try runs at once, each try after waits 100ms, and a session that stays up for 1s clears that wait. The server keeps undelivered evictions and lock wake-ups for 8s; a rejoin inside the window receives them.
  • Websocket. Same heartbeat, plus a ping every 2s answered with a pong. Six seconds of silence, or a dropped socket, fails the calls in flight and dials again. The mount stays up; the retry wait matches POST.
  • A signed id the server has not seen is a new mount. An id whose signature does not match the token is refused. Inodes still die with the server process — a restart means remount.
